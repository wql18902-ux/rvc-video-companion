## 已验证无效方案

- **MV3 扩展 CSP 写 `'wasm-eval'`**（MV2 旧关键字）→ Chrome 直接拒载扩展（"Insecure CSP value 'wasm-eval'"）。MV3 只认 `'wasm-unsafe-eval'`。2026-07-31 实测
- **扩展消息通道（content↔SW↔offscreen）传 File/Blob/ArrayBuffer** → 全链路走 JSON 序列化，二进制对象退化成空对象 `{}`（字符串 100% 保真）。2026-07-31 三次实测（File 退化、ArrayBuffer 也退化）。正确做法：二进制一律 base64 字符串分片传递
- **裸调 ffmpeg-core 的 `Module._ffmpeg(argc, argv)`** → 该定制构建正常执行完也抛 `Aborted()` 异常被误报失败、且时有时无。正确做法：用官方 `Module.exec(...)` 入口（自带 DEFAULT_ARGS `./ffmpeg -nostdin -y`，退出码读 `Module["ret"]`，exec 内部捕获 Aborted 正常退出）。日志用 `setLogger()` 注册（print/printErr 工厂参数被 UMD 包装覆盖）。2026-07-31 实测
- **转码后 finally 清理调 `Module._free`** → 此 core 构建未导出 `_free`，报错。缺失时容错跳过（offscreen 短生命周期可接受）

- content.js 用 `<script>` 标签注入 mpegts.min.js → 扩展隔离世界永远拿不到 `window.mpegts`，确定性失败，不是偶发。正确做法：manifest content_scripts 里声明，同世界共享
- 所有格式一刀切走 ffmpeg 实时转码 → 原生能播的 MP4 也被绑上转码链，链一抖全挂。正确做法：按扩展名分流，原生能播的绝不转码
- **ffmpeg.wasm 跑在 content script（注入第三方页面）里** -> 2026-07-30 搜证（ffmpeg.wasm issue #337、web.dev、Stack Overflow，均 A 级来源）：content script 受宿主页 CSP 和跨源隔离约束，控制不了 COOP/COEP；多线程版需 SharedArrayBuffer+COOP/COEP 跑不了；单线程版不需要但「CPU blocking, freezes the UI, sometimes browser crashes」且不能跑在 worker。所有成功案例都把 ffmpeg.wasm 放在扩展自己的页面（options/popup/sandbox/offscreen）。结论：嵌入式（注入第三方页）+ MKV（需 ffmpeg 转码）+ 零本地 server，三者凑不齐。要同时满足必须上 chrome.offscreen document 架构，工程量大且 wasm 转码性能约本地 ffmpeg 0.5-0.8 倍，实时看高清 MKV 易卡
- **ffmpeg.wasm MEMFS 处理大文件（>200MB）** -> 2026-07-31 实测，offscreen.js v1-v5 共 5 轮修复全部失败。错误从 `reading 'name'` 演变到 `reading 'size'`，每次在不同位置出现 null 引用。根因是 Emscripten MEMFS 文件节点在存储数组扩容时发生内部损坏，null 引用在 ffmpeg-core.js 库代码深处触发（`FS.stat` → `node_ops.getattr` → `node.contents` 为 null），无法在不 fork 库的情况下拦截。系统化调试结论：3+ 次修复失败 = 架构级问题，非 bug。决策：废弃 WASM 上架版，内部版（本地 ffmpeg 服务器）为唯一方案

## 登记在案的下一步

- **方案 A（备选重构）**：MKV 首次点击转 MP4 缓存（视频流 copy 不重编码，一部电影一两分钟），之后秒开，彻底砍掉实时转码和 mpegts.js。B 路线固有毛病（假进度条、高 CPU、seek 重启转码流）烦到用户时启动
- **死代码清理**：`reader-video-companion/player.html`（16.9KB）无任何引用（实际服务的是 stream-server/player.html），两份并存是漂移温床，建议删除——等用户确认
- **媒体键退路**：若 macOS 媒体键路由不生效，改 pynput 全局热键（需给终端授辅助功能权限一次）
- **WASM 上架版已废弃并删除（2026-07-31）**：5 轮修复失败，根因 Emscripten MEMFS 无法处理 >200MB 文件。`reader-video-companion-wasm/` 目录已清理。分发改为内部版 zip 包（`packaging/make-distro.sh` → `packaging/dist/RVC视频伴侣.zip` 25MB）
- **h264_videotoolbox 转码回归（2026-07-31，已解决）**：server.py 从 `libx264 -preset fast -crf 23` 改为 `h264_videotoolbox -b:v 2M`，ffmpeg benchmark 更快但用户实测浏览器流式播放看不了/更慢。已回滚为 libx264，打包版 .app 已重建。教训：改编码器不能只跑 ffmpeg benchmark，必须端到端浏览器流式播放验证（验收 sample.mp4 太小不暴露问题）
- **build.sh dylib 收集修复（2026-07-31，已解决）**：旧版硬编码匹配 `/opt/homebrew/` 路径，TRAE 环境中 ffmpeg 路径不同导致 `staging/ffmpeg/lib/` 为空。改为 `otool -L` + `@rpath`/`@loader_path` 递归解析，17 个 dylib 正确打包。打包版 .app（57MB）和分发包（24MB）已重建。
