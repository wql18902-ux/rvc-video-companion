## 问题清单（按严重程度）

### P0-1 ｜ release 与代码严重不符（致命）

**现象**：release notes 说 [v3] 用 `open -a Finder`（LaunchServices，无 TCC）修了 -1708；实际 f913155 代码是 `activate me`。

**证据**：
```
# f913155 (release 构建点) server.py:497
'activate me',
'-e', 'set f to choose folder',

# 同文件注释（release 自己写的）
# 对话框可能不自动前置，用户需从 Dock 点访达
```

**后果**：release 自己承认对话框不前置。用户点浏览 → 对话框躲在浏览器后面 → 必须手动点 Finder/文件才看到 → 完全符合你描述的"要点文件才跳出系统按钮"。

**根因**：release notes 是"计划写的修复"，代码只完成了 `activate me`（v2），`open -a Finder`（v3）从未落地。

### P0-2 ｜ 访达对话框前置方案不可靠（致命）

**现状代码**（未提交工作区）：
```python
['osascript', '-e',
 'activate application "Finder"',      # ← 未提交改动，方向对
 '-e', 'set f to choose folder',
 '-e', 'return POSIX path of f']
```

**问题**：`activate application "Finder"` 在 osascript 上下文激活的是 Finder 应用窗口，但 `choose folder` 对话框归属 osascript 进程，经验上仍可能不前置。

**可靠方案**（release notes 声称但未实现的那个）：分两步
```python
# 步骤1：LaunchServices 激活 Finder（无 TCC 权限弹窗）
subprocess.run(['open', '-a', 'Finder'])
# 步骤2：纯 Standard Additions choose folder（无 TCC）
result = subprocess.run(['osascript', '-e',
    'set f to choose folder',
    '-e', 'return POSIX path of f'], ...)
```

### P0-3 ｜ 改键无效根因：release 完全没有按键同步链路（致命）

**验证**：`git show f913155:reader-video-companion/content.js | grep -c pushKeybindingsToServer` = **0**
`git show f913155:stream-server/server.py | grep -c "set-keybindings\|--bindings"` = **0**

**release 里的改键行为**：改键只写 `chrome.storage.local`，全局热键子进程始终用硬编码的 s/a/d。所以"改了键还是 s/a/d"是必然的。

**未提交工作区已有完整修复**（设计正确，链路完整）：

| 环节 | 文件 | 实现 |
|------|------|------|
| 前端推送 | content.js | `pushKeybindingsToServer()` → POST `/api/set-keybindings` |
| 前端触发 | content.js | `saveKeybindings()` 后调推送；初始化时也推送 |
| 后端接收 | server.py | `serve_set_keybindings()` 校验（仅 a-z0-9 单字符，防 IME 脏值） |
| 后端持久化 | server.py | `save_keybindings()` → `~/.rvc/keybindings.json` |
| 后端重启 | server.py | `restart_hotkey_listener()` terminate 旧子进程 + 启新 |
| 子进程接收 | server.py | `run_hotkey_child()` 解析 `--bindings` → `char_to_action` 映射 |
| 子进程执行 | server.py | `on_press` 查 `char_to_action` 表，不再硬编码 s/a/d |

**评价**：这套链路设计是对的，校验严格（防 IME 脏值），持久化合理，重启逻辑正确（先 terminate 再 start）。**可以直接用**。

### P1-1 ｜ "卡顿感"根因：交互反馈缺失，非性能瓶颈

**已排除**：HTTP server 用 `ThreadedHTTPServer`（ThreadingMixIn），多线程，choose folder 阻塞不卡全局。

**真实根因**：
1. 点浏览 → 对话框不前置 → 用户以为没反应 → 焦虑等待 = "卡"
2. `checkServer()` 用 `/api/files?dir=~/Downloads` 检测，每次扫整个 Downloads 目录；应改用 `/api/health`（已有，轻量）

**结论**：修好访达前置后，"卡"感会消失。不是性能问题，是交互问题。

---

### P1-2 ｜ osascript 同步阻塞 60s

`serve_pick_folder` 用 `subprocess.run(timeout=60)` 同步等 osascript。ThreadingHTTPServer 下不卡其他请求，但：
- 用户点浏览后，前端 fetch 等 60s 才返回
- 对话框开着期间，那个请求线程被占
- 可接受，但前端应有"正在弹出访达，请查看 Dock/桌面"的即时提示
